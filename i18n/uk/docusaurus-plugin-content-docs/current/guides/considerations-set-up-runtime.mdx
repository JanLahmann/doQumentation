# Міркування щодо налаштування IBM Quantum Platform для організації {#considerations-for-setting-up-ibm-quantum-platform-for-an-organization}

IBM Quantum&reg; Platform — це панель керування для екземплярів IBM Quantum Compute Service та навантажень твого облікового запису IBM Cloud&reg;, а також надає спрощений вигляд керування доступом. Обліковий запис IBM Cloud організації може мати кількох користувачів і кілька екземплярів Quantum Compute, кожен зі своїм власним розподілом. Identity and Access Management (IAM) контролює, які користувачі можуть отримати доступ до яких екземплярів сервісу, тож ти можеш забезпечити співпрацю, обмежуючи видимість там, де це потрібно. Керування доступом стає більш актуальним, якщо у тебе є екземпляри сервісу на платних планах. Дивись [Структура облікового запису IBM Cloud](/guides/cloud-account-structure) для огляду того, як облікові записи, користувачі, екземпляри та доступ поєднуються між собою. Зверніться до [документації IBM Cloud IAM](https://cloud.ibm.com/docs/account?topic=account-iamoverview) для повних деталей про концепції IAM, згадані в цьому посібнику, такі як групи доступу, політики, ролі та групи ресурсів.

Цей посібник описує рішення та компроміси, пов'язані з налаштуванням доступу для організації з кількома екземплярами сервісу &mdash; наприклад, призначення одного екземпляра на команду або навантаження.

<Admonition type="note">
If your organization has multiple IBM Cloud accounts &mdash; for example, separate accounts per business unit, each with its own Quantum Compute instances &mdash; you can link them under a single IBM Cloud Enterprise account, which has one main account responsible for billing and one or more child accounts. To redistribute Premium or Flex Plan allocation between child accounts, contact IBM Quantum support through the [IBM Cloud Support Center](https://cloud.ibm.com/unifiedsupport/cases/form). See the [IBM Cloud Enterprise account documentation](https://cloud.ibm.com/docs/account?topic=account-what-is-enterprise) for full details.
</Admonition>

## Огляд {#overview}

   <Admonition type="note">
   IBM Cloud&reg; provides several ways to implement the mechanisms described in this guide. Most of the steps are generic to IBM Cloud and not specific to Quantum Compute, except the custom role details.
</Admonition>

### Задіяні персони {#involved-personas}

У цьому посібнику згадуються такі персони:

* **Користувач**: Людина, яка отримує доступ до ресурсів Quantum Compute (_екземплярів сервісу_) і може потенційно співпрацювати з іншими користувачами над цими ресурсами. Доступ користувачів контролюється адміністратором, і вони не можуть створювати або видаляти екземпляри сервісу.

* **Адміністратор хмари**: Власник облікового запису IBM Cloud, який володіє ресурсами IBM Quantum Compute і керує тим, які користувачі можуть отримувати до них доступ. Як власник ресурсів, адміністратор несе витрати за будь-яке платне використання ресурсів.

* **Адміністратор IDP**: Адміністратор, який визначає ідентичності та їхні атрибути в постачальнику ідентичностей (IDP).


### Термінологія {#terminology}

У цьому посібнику використовуються такі терміни:

* _Ресурс_: Загальний термін IBM Cloud, що позначає об'єкт, яким можна керувати через інтерфейс користувача Cloud, CLI або API. У цьому посібнику _ресурс_ — це екземпляр IBM Quantum Compute Service.

* _Екземпляр сервісу_: Екземпляр сервісу використовується для доступу до хмарних сервісів — зокрема, до квантових комп'ютерів через IBM Quantum Compute Service. Він визначається через каталог. Можна визначити кілька екземплярів сервісу на основі однакових або різних планів, що надають доступ до різних квантових обчислювальних бекендів. Докладніше дивись у розділі [Доступні плани IBM Cloud](/guides/plans-overview).

## Сплануй своє налаштування {#plan-your-setup}

Перш ніж налаштовувати IBM Quantum Platform для своєї організації, потрібно прийняти такі рішення:

* **Як визначаються ідентичності користувачів?** Можна налаштувати користувачів IBM Cloud, користувачів з іншого постачальника ідентичностей (IDP) або поєднати обидва варіанти.

   * Якщо ти використовуєш інший IDP, хто призначає користувачів до груп доступу — адміністратор хмари чи адміністратор IDP?

   * Якщо адміністратор IDP призначає користувачів за допомогою динамічних правил, тобі знадобиться користувацький атрибут користувача IDP для використання як ключа відповідності (наприклад, атрибут `team`).

* **Скільки екземплярів сервісу тобі потрібно і для чого буде використовуватися кожен з них?** Плануй назви екземплярів ретельно. Щоразу, коли ти створюєш екземпляр сервісу через інтерфейс користувача IBM Quantum Platform, платформа робить додатковий виклик до IAM від твого імені, щоб створити відповідну групу доступу (з тією самою назвою, що й екземпляр, з доданим "Collaborators"), яка надає право запису до цього екземпляра. Тому назви екземплярів також стають назвами груп доступу. Цей додатковий крок відбувається лише тоді, коли ти створюєш екземпляр через інтерфейс користувача IBM Quantum Platform. Це не відбувається, якщо ти створюєш екземпляр за допомогою Terraform, IBM Cloud CLI або IBM Cloud API.

   * Навантаження належать екземплярам сервісу, і користувачі, які мають доступ до екземпляра, можуть бачити його навантаження.

   * Екземпляри сервісу можуть базуватися на різних планах, надаючи доступ до різних бекендів і розподілів.

* **Яким користувачам потрібен доступ до яких екземплярів сервісу?**

* **Чи повинні користувачі мати можливість видаляти робочі навантаження?** Зберігання робочих навантажень в екземплярах сервісу дає більше можливостей для відстеження витрат на виставлення рахунків.

* **Чи будеш ти використовувати групу доступу, яка автоматично створюється для кожного екземпляра, створювати додаткові власні групи доступу, надавати доступ окремим користувачам безпосередньо, чи організовувати екземпляри в групи ресурсів?**

   * **Групи доступу** — це зручний і поширений спосіб контролю доступу користувачів до ресурсів IBM Cloud. Кожен екземпляр сервісу, який ти створюєш через інтерфейс користувача IBM Quantum Platform, вже має власну групу доступу "Collaborators". Ти можеш використовувати цю групу як є, або створити додаткові групи доступу в консолі IBM Cloud, щоб групувати користувачів за командою або навантаженням (наприклад, `ml` та `finance`) для одного або кількох екземплярів. Кожна група доступу використовує користувацьку роль, яка дозволяє користувачам отримувати доступ до певних екземплярів сервісу або груп ресурсів. Якщо тобі не потрібно, щоб група користувачів мала однаковий доступ, ти також можеш надати доступ окремим користувачам безпосередньо, без групи доступу.

      * Якщо ти використовуєш динамічні правила на основі атрибутів IDP для призначення користувачів до груп доступу, уникай значень атрибутів, які є підрядками одне одного. Наприклад, якщо ти використовуєш `ml` і `chemlab` як значення атрибутів, правило, що відповідає `ml`, також відповідатиме `chemlab`, ненавмисно надаючи більше доступу, ніж очікується. Використовуй унікальні значення, такі як `ml` і `chem-lab`, або додай префікси чи суфікси, щоб уникнути ненавмисних збігів підрядків.

   * **Групи ресурсів** використовуються лише тоді, коли потрібно підтримувати чітке розмежування екземплярів сервісу. Під час створення екземпляра сервісу з IBM Quantum Platform ти можеш обрати, до якої групи ресурсів він належить (і додати теги), але для створення або керування групами ресурсів необхідно використовувати консоль IBM Cloud. Якщо в групі ресурсів створюються нові екземпляри сервісу, усі користувачі, які мають доступ до групи ресурсів, бачать їх автоматично, без оновлення груп доступу. Якщо ти вирішиш використовувати групи ресурсів, спочатку створи групи доступу, а потім признач їх групам ресурсів.


   <Admonition type="note">
   A service instance can belong to only one resource group, and that assignment cannot be changed after the instance is created. Therefore, resource groups might not provide enough flexibility if service instances might need to move between resource groups later.
   </Admonition>

## Міркування {#considerations}

Під час налаштування середовища слід враховувати такі аспекти.

### Визначення більш деталізованих ролей {#define-more-fine-grained-roles}

Користувацькі ролі можна використовувати для більш деталізованого контролю доступу. Наприклад, деяким користувачам може знадобитися повний доступ для роботи з екземплярами сервісу, тоді як іншим — лише доступ на читання до екземплярів сервісу, програм та робочих навантажень.

Щоб досягти цього, визнач дві різні користувацькі ролі, наприклад `MLreader` і `MLwriter`. Видали всі дії скасування, видалення та оновлення з користувацької ролі `MLreader`, а до `MLwriter` включи всі дії. Потім додай ці ролі до двох різних груп доступу відповідно.

<Admonition type="note">
When using dynamic rules, that is, when the IDP administrator manages access through custom IDP user attributes, do not use IDP custom user attributes that are substrings of each other. For instance, don't use `ml` and `mlReader`, as the string comparison of `ml` would also accept `mlReader`. You could use `MLreader` and `MLwriter` to avoid this conflict.
</Admonition>

Для прикладу дивись [Налаштування користувацьких ролей](/guides/custom-roles#custom).

<span id="shared-access"></span>

### Спільний доступ до навантаження {#shared-workload-access}

Доступ застосовується до екземплярів сервісу. Таким чином, користувачі з правом запису до екземпляра (включно з правом через групу доступу "Collaborators", автоматично створену для екземплярів, зроблених через інтерфейс користувача IBM Quantum Platform) можуть скасовувати власні навантаження, але також можуть переглядати й скасовувати навантаження інших користувачів у цьому екземплярі. Це особливість роботи IAM, яку неможливо змінити.

<span id="nest-org"></span>

### Моделювання ієрархічних структур {#simulate-hierarchical-structures}

За замовчуванням доступ до кожного екземпляра сервісу керується незалежно, наприклад, через групу доступу "Collaborators", автоматично створену для екземплярів, зроблених через інтерфейс користувача IBM Quantum Platform. IAM не має вбудованої ієрархії груп, але ти можеш наблизитися до неї, створюючи групи доступу, які посилаються на екземпляри сервісу кількох команд. Користувачам, яким потрібен широкий доступ, потрібно лише додати їх до однієї групи "верхнього рівня", замість того, щоб додавати їх до кожної окремої групи доступу команди.

<span id="repeat-org"></span>

### Послідовне та відтворюване розгортання конфігурації {#consistent-and-repeatable-deployment-of-the-configuration}

Кроки цього посібника можна автоматизувати для послідовного та відтворюваного управління користувачами, екземплярами сервісу та зіставленнями доступу між ними. Звернись до [документації Terraform IBM Cloud® Provider](https://registry.terraform.io/providers/IBM-Cloud/ibm/latest/docs) для отримання шаблонів.

Можна використовувати Terraform для встановлення розподілу та лімітів, а також обмеження доступу до бекенду для екземплярів сервісу `quantum-computing`. Дивись [Початок роботи з Terraform на IBM Cloud](https://cloud.ibm.com/docs/ibm-cloud-provider-for-terraform?topic=ibm-cloud-provider-for-terraform-getting-started) для отримання додаткової інформації.

Приклад:

```terraform
resource "ibm_resource_instance" "instance1" {
  name       = "name"
  service    = "quantum-computing"
  plan       = "premium"
  location   = "us-east"
  parameters = {
    usage_allocation_seconds = "10" # Mandatory
    usage_limit_seconds      = "20" # Optional. If omitted, it can
            # continue using time after reaching the allocation
    backends                 = ["ibm_boston"] # Optional
  }
}
```
