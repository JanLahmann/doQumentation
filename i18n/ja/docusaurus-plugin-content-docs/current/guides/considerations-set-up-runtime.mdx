# 組織向けIBM Quantum Platformのセットアップに関する考慮事項 {#considerations-for-setting-up-ibm-quantum-platform-for-an-organization}

IBM Quantum&reg; Platformは、IBM Cloud&reg;アカウントのIBM Quantum Compute Serviceインスタンスとワークロードのダッシュボードであり、アクセス管理の簡略化されたビューを提供します。組織のIBM Cloudアカウントは、複数のユーザーと複数のQuantum Computeインスタンスを持つことができ、それぞれに独自の割り当てがあります。Identity and Access Management（IAM）は、どのユーザーがどのサービスインスタンスにアクセスできるかを制御するため、必要に応じて可視性を制限しながらコラボレーションを可能にします。有料プランのサービスインスタンスがある場合、アクセス管理の重要性が高まります。アカウント、ユーザー、インスタンス、アクセスがどのように連携するかの概要については、[IBM Cloudアカウント構造](/guides/cloud-account-structure)を参照してください。このガイドで参照されているアクセスグループ、ポリシー、ロール、リソースグループなどのIAMの概念の詳細については、[IBM Cloud IAMドキュメント](https://cloud.ibm.com/docs/account?topic=account-iamoverview)を参照してください。

このガイドでは、複数のサービスインスタンスを持つ組織のアクセスを設定する際に関わる決定事項とトレードオフについて説明します&mdash;たとえば、チームまたはワークロードごとに1つのインスタンスを割り当てる場合などです。

<Admonition type="note">
If your organization has multiple IBM Cloud accounts &mdash; for example, separate accounts per business unit, each with its own Quantum Compute instances &mdash; you can link them under a single IBM Cloud Enterprise account, which has one main account responsible for billing and one or more child accounts. To redistribute Premium or Flex Plan allocation between child accounts, contact IBM Quantum support through the [IBM Cloud Support Center](https://cloud.ibm.com/unifiedsupport/cases/form). See the [IBM Cloud Enterprise account documentation](https://cloud.ibm.com/docs/account?topic=account-what-is-enterprise) for full details.
</Admonition>

## 概要 {#overview}

   <Admonition type="note">
   IBM Cloud&reg; provides several ways to implement the mechanisms described in this guide. Most of the steps are generic to IBM Cloud and not specific to Quantum Compute, except the custom role details.
</Admonition>

### 関連するペルソナ {#involved-personas}

このガイドでは、以下のペルソナが言及されています。

* **ユーザー**: Quantum Compute リソース（_サービスインスタンス_）へのアクセス権を持ち、これらのリソースについて他のユーザーとコラボレーションできる人物。ユーザーのアクセスは管理者によって制御され、サービスインスタンスの作成・削除はできません。

* **クラウド管理者**: IBM Quantum Compute リソースを所有し、どのユーザーがこれらのリソースにアクセスできるかを管理するIBM Cloudアカウントオーナー。リソースオーナーとして、有料リソースの使用料金が請求されます。

* **IDP管理者**: IDプロバイダー（IDP）でIDおよびその属性を定義する管理者。


### 用語 {#terminology}

このガイドでは以下の用語を使用します。

* _リソース_: Cloud UIやCLI、APIを通じて管理できるオブジェクトを指す汎用的なIBM Cloud用語。このガイドでは、_リソース_は Quantum Compute Service インスタンスを指します。

* _サービスインスタンス_: Cloudサービス、具体的には IBM Quantum Compute Service を通じた量子コンピューターへのアクセスに使用されます。カタログを通じて定義され、異なる量子コンピューティングBackendへのアクセスを提供するさまざまなプランに基づいて、複数のサービスインスタンスを定義できます。詳細は[利用可能なIBM Cloudプラン](/guides/plans-overview)を参照してください。

## セットアップの計画 {#plan-your-setup}

組織向けにIBM Quantum Platformをセットアップする前に、以下の点を決定する必要があります。

* **ユーザーIDはどのように定義しますか？** IBM Cloudユーザー、別のアイデンティティ・プロバイダー（IDP）のユーザー、またはその両方を設定できます。

   * 別のIDPを使用する場合、クラウド管理者またはIDP管理者がユーザーをアクセスグループに割り当てますか？

   * IDP管理者が動的ルールを通じてユーザーを割り当てる場合、マッチングキーとして使用するカスタムIDPユーザー属性（たとえば`team`属性）が必要です。

* **サービスインスタンスはいくつ必要で、それぞれ何に使用しますか？** インスタンス名は慎重に計画してください。IBM Quantum Platformのユーザーインターフェースを通じてサービスインスタンスを作成するたびに、プラットフォームはユーザーに代わってIAMへの追加の呼び出しを行い、そのインスタンスへの書き込みアクセスを許可する対応するアクセスグループ（インスタンスと同じ名前に「Collaborators」を付加したもの）を作成します。そのため、インスタンス名はアクセスグループ名にもなります。この追加のステップは、IBM Quantum Platformのユーザーインターフェースを通じてインスタンスを作成した場合にのみ発生します。Terraform、IBM Cloud CLI、またはIBM Cloud APIを使用してインスタンスを作成した場合には発生しません。

   * ワークロードはサービスインスタンスに属し、インスタンスへのアクセス権を持つユーザーはそのワークロードを確認できます。

   * サービスインスタンスは異なるプランに基づくことができ、異なるBackendおよび割り当てへのアクセスを提供します。

* **どのユーザーがどのサービスインスタンスにアクセスする必要がありますか？**

* **ユーザーはワークロードを削除できるべきですか？** サービスインスタンスにワークロードを保持することで、請求コストのトレーサビリティが向上します。

* **各インスタンスに対して自動的に作成されるアクセスグループを使用しますか、それとも独自の追加のアクセスグループを作成しますか、個々のユーザーに直接アクセス権を割り当てますか、あるいはインスタンスをリソースグループに整理しますか？**

   * **アクセスグループ**は、IBM Cloudリソースへのユーザーアクセスを制御するための便利で一般的な方法です。IBM Quantum Platformのユーザーインターフェースを通じて作成する各サービスインスタンスには、すでに独自の「Collaborators」アクセスグループがあります。そのグループをそのまま使用することも、IBM Cloudコンソールで追加のアクセスグループを作成して、1つまたは複数のインスタンスにわたってチームまたはワークロードごとにユーザーをグループ化する（たとえば`ml`や`finance`）こともできます。各アクセスグループは、ユーザーが特定のサービスインスタンスまたはリソースグループにアクセスできるようにするカスタムロールを使用します。ユーザーのグループが同じアクセスを共有する必要がない場合は、アクセスグループを使わずに個々のユーザーに直接アクセス権を割り当てることもできます。

      * IDP属性に基づく動的ルールを使用してユーザーをアクセスグループに割り当てる場合、互いの部分文字列となる属性値は避けてください。たとえば、`ml`と`chemlab`を属性値として使用すると、`ml`にマッチするルールは`chemlab`にもマッチしてしまい、意図せず想定以上のアクセスが付与されます。`ml`と`chem-lab`のような一意の値を使用するか、意図しない部分文字列マッチを避けるためにプレフィックスやサフィックスを追加してください。

   * **リソースグループ**は、サービスインスタンスを明確に分離する必要がある場合にのみ使用します。IBM Quantum Platformからサービスインスタンスを作成する際に、そのインスタンスが属するリソースグループを選択できます（タグを追加することもできます）が、リソースグループの作成や管理にはIBM Cloudコンソールを使用する必要があります。リソースグループにさらにサービスインスタンスが作成されると、そのリソースグループへのアクセス権を持つすべてのユーザーは、アクセスグループを更新せずに自動的にそれらを確認できるようになります。リソースグループを使用する場合は、まずアクセスグループを作成してから、それらをリソースグループに割り当てます。


   <Admonition type="note">
   A service instance can belong to only one resource group, and that assignment cannot be changed after the instance is created. Therefore, resource groups might not provide enough flexibility if service instances might need to move between resource groups later.
   </Admonition>

## 考慮事項 {#considerations}

環境をセットアップする際は、以下の考慮事項を理解しておく必要があります。

### より細かい粒度のロールを定義する {#define-more-fine-grained-roles}

カスタムロールは、より細かい粒度のアクセス制御に使用できます。たとえば、サービスインスタンスで完全なアクセス権が必要なユーザーと、サービスインスタンス、プログラム、ワークロードへの読み取りアクセスのみが必要なユーザーがいる場合があります。

それを実現するには、`MLreader`と`MLwriter`などの2つの異なるカスタムロールを定義します。`MLreader`カスタムロールからすべてのキャンセル、削除、更新アクションを削除し、`MLwriter`カスタムロールにすべてのアクションを含めます。次に、それぞれのロールを2つの異なるアクセスグループに追加します。

<Admonition type="note">
When using dynamic rules, that is, when the IDP administrator manages access through custom IDP user attributes, do not use IDP custom user attributes that are substrings of each other. For instance, don't use `ml` and `mlReader`, as the string comparison of `ml` would also accept `mlReader`. You could use `MLreader` and `MLwriter` to avoid this conflict.
</Admonition>

例については、[カスタムロールの設定](/guides/custom-roles#custom)を参照してください。

<span id="shared-access"></span>

### 共有ワークロードのアクセス {#shared-workload-access}

アクセスはサービスインスタンスに適用されます。したがって、インスタンスへの書き込みアクセス権を持つユーザー（IBM Quantum Platformのユーザーインターフェースによって作成されたインスタンスに対して自動的に作成される「Collaborators」アクセスグループを通じたアクセスを含む）は、自分自身のワークロードをキャンセルできますが、そのインスタンス内の他のユーザーのワークロードを表示およびキャンセルすることもできます。これはIAMの仕組みによるものであり、変更することはできません。

<span id="nest-org"></span>

### 階層構造をシミュレートする {#simulate-hierarchical-structures}

デフォルトでは、各サービスインスタンスのアクセスは、たとえばIBM Quantum Platformのユーザーインターフェースを通じて作成されたインスタンスに対して自動的に作成される「Collaborators」アクセスグループを通じて、独立して管理されます。IAMにはグループの組み込みの階層構造はありませんが、複数のチームのサービスインスタンスを参照するアクセスグループを作成することで、それに近い構造を実現できます。広範なアクセスが必要なユーザーは、各チーム個別のアクセスグループではなく、1つの「トップレベル」グループに追加するだけで済みます。

<span id="repeat-org"></span>

### 設定の一貫した繰り返し可能なデプロイ {#consistent-and-repeatable-deployment-of-the-configuration}

このガイドの手順は、ユーザー、サービスインスタンス、およびそれらのアクセスマッピングを一貫して繰り返し管理するために自動化できます。テンプレートについては[Terraform IBM Cloud&reg; Providerドキュメント](https://registry.terraform.io/providers/IBM-Cloud/ibm/latest/docs)を参照してください。

Terraformを使用して、割り当てと制限の設定、および`quantum-computing`サービスインスタンスのBackendアクセスの制限を行うことができます。詳細については、[IBM CloudでのTerraformの使用開始](https://cloud.ibm.com/docs/ibm-cloud-provider-for-terraform?topic=ibm-cloud-provider-for-terraform-getting-started)を参照してください。

例：

```terraform
resource "ibm_resource_instance" "instance1" {
  name       = "name"
  service    = "quantum-computing"
  plan       = "premium"
  location   = "us-east"
  parameters = {
    usage_allocation_seconds = "10" # Mandatory
    usage_limit_seconds      = "20" # Optional. If omitted, it can
            # continue using time after reaching the allocation
    backends                 = ["ibm_boston"] # Optional
  }
}
```
