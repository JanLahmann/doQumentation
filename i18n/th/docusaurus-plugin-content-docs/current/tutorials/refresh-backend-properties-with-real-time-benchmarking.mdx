## ความเป็นมา {#background}

IBM Quantum&reg; QPU ทุกตัวรายงานชุดคุณสมบัติที่อธิบายว่าคิวบิตแต่ละตัวทำงานได้ดีเพียงใดในปัจจุบัน: เวลา relaxation ($T_1$), เวลา coherence ($T_2$), readout error, และ error ของ gate หนึ่งและสองคิวบิต ตัวเลขเหล่านี้มีความสำคัญในทางปฏิบัติ transpiler ใช้ตัวเลขเหล่านี้เพื่อตัดสินใจว่าคิวบิตทางกายภาพใดที่ Circuit ของคุณควรรัน เทคนิคการลด error อาศัยตัวเลขเหล่านี้ และคุณอาจใช้ตัวเลขเหล่านี้เพื่อตัดสินว่าอุปกรณ์ทำงานได้ดีเพียงพอสำหรับการทดลองหรือไม่

คุณสมบัติที่รายงานมาจากกระบวนการ calibration ซึ่งโดยทั่วไปจะรันประมาณวันละครั้ง อย่างไรก็ตาม คิวบิตแบบตัวนำยิ่งยวดสามารถ drift ได้ในช่วงเวลาที่สั้นกว่า และข้อบกพร่องชั่วคราว (ที่เรียกว่า two-level system) สามารถทำให้คิวบิตที่ดูดีเยี่ยมในเวลา calibration เสื่อมสภาพลงชั่วคราวได้ นอกจากนี้ job มักจะถูก transpile ไว้ก่อนที่จะรันจริงนานพอสมควร ดังนั้นการตัดสินใจที่อิงจากคุณสมบัติที่รายงานอาจตั้งอยู่บนข้อมูลที่ล้าสมัย tutorial [การ benchmark แบบ real-time สำหรับการเลือกคิวบิต](/tutorials/real-time-benchmarking-for-qubit-selection) แสดงให้เห็นว่าคุณสมบัติเหล่านี้สามารถผันผวนได้มากเพียงใดในแต่ละวัน และสร้างเวิร์กโฟลว์ characterization แบบเต็มด้วยมือจาก [Qiskit Experiments](https://qiskit-community.github.io/qiskit-experiments/) แต่ละตัว

tutorial นี้แสดงเวอร์ชันที่คล่องตัวของเวิร์กโฟลว์นั้น โดยใช้ยูทิลิตี้ `BackendCharacterization` จาก [Qiskit Device Benchmarking](https://github.com/qiskit-community/qiskit-device-benchmarking) ซึ่งรวมการสร้างการทดลอง, การส่ง job, และการ fit เส้นโค้งไว้ในการเรียกไม่กี่ครั้ง คุณใช้เวลา QPU ประมาณ 70 วินาที และได้ออบเจ็กต์ backend ที่มีคุณสมบัติสะท้อนอุปกรณ์ *ในขณะนี้* พร้อมที่จะเปรียบเทียบกับค่าที่รายงาน หรือส่งต่อไปยังเครื่องมือขั้นถัดไป

### การทดลอง characterization {#the-characterization-experiments}

suite นี้วัดคุณสมบัติห้าอย่าง แต่ละอย่างมีการทดลองมาตรฐาน:

- **Readout error** (`readout`): คิวบิตแต่ละตัวถูกเตรียมใน $|0\rangle$ หรือ $|1\rangle$ และวัดทันที ความน่าจะเป็นของการอ่าน state ผิดให้ error ของ state preparation and measurement (SPAM)

- **Error ของ gate หนึ่งคิวบิต** (`rb_1q`): Randomized benchmarking (RB) รันลำดับของ single-qubit Clifford gate แบบสุ่มที่ในอุดมคติจะรวมกันเป็น identity วิธีที่ความน่าจะเป็นในการอยู่รอดสลายตัวไปตามความยาวของลำดับให้ error เฉลี่ยต่อ gate โดยไม่ขึ้นกับ error ของ SPAM

- **ความผิดพลาดของ Gate สองคิวบิต** (`rb_2q`): แนวคิด RB แบบเดียวกันที่นำไปใช้กับเลเยอร์ทั้งหมดของ Gate สองคิวบิตที่ไม่ทับซ้อนกันซึ่งรันพร้อมกัน เหมือนกับการทดลอง [layer fidelity](https://arxiv.org/abs/2311.05933) เนื่องจากมี Gate จำนวนมากรันพร้อมกัน อัตราความผิดพลาดที่ได้จึงรวมผลของ crosstalk และใกล้เคียงกับสิ่งที่ Circuit ที่ลึกจะเจอจริง ๆ มากกว่า

- **$T_1$** (`t1`): แต่ละคิวบิตจะถูกกระตุ้นและวัดหลังจากดีเลย์ที่เพิ่มขึ้นเรื่อย ๆ การสลายตัวของสัดส่วนสถานะกระตุ้นให้ค่าเวลาผ่อนคลาย (relaxation time)

- **$T_2$** (`t2`): การทดลอง Hahn echo จะทำให้แต่ละคิวบิตอยู่ในสถานะซ้อนทับ (superposition) ใช้พัลส์ echo ที่กึ่งกลางของดีเลย์ และวัดว่าความเชื่อมโยงเฟส (phase coherence) หายไปเร็วแค่ไหน โดยค่าเริ่มต้นจะใช้ echo เดียว ส่วนแบบหลาย echo (แบบ CPMG) จะสาธิตในตอนท้ายของบทเรียนนี้


### สิ่งที่การรีเฟรชทำและไม่ทำ {#what-refreshing-does-and-does-not-do}

จำสามประเด็นนี้ไว้เมื่อใช้เวิร์กโฟลว์นี้:

- คุณสมบัติที่รีเฟรชแล้วจะอยู่เฉพาะใน backend object ที่ส่งคืนให้คุณเท่านั้น ไม่มีอะไรเปลี่ยนแปลงบนอุปกรณ์เองหรือในข้อมูลการปรับเทียบ (calibration) ที่ IBM Quantum รายงานให้ผู้ใช้คนอื่น

- ค่าที่วัดได้เป็นภาพรวม (snapshot) ที่ถ่ายด้วยวิธีการเฉพาะ ค่าบางส่วน โดยเฉพาะความผิดพลาดของ Gate สองคิวบิตแบบเลเยอร์และค่า $T_2$ แบบ single-echo ที่วัดพร้อมกัน จะถูกวัดด้วยวิธีที่ต่างจากข้อมูลการปรับเทียบที่รายงานไว้ ดังนั้นส่วนหนึ่งของช่องว่างที่คุณสังเกตเห็นจึงเกิดจากวิธีการมากกว่าการดริฟต์ บทเรียนนี้จะชี้ให้เห็นว่าจุดไหนที่เป็นเช่นนั้น

- การจำแนกคุณลักษณะ (characterization) เองก็ใช้เวลา QPU (ประมาณ 70 วินาทีสำหรับชุดเต็มบนโปรเซสเซอร์ Heron r2) ซึ่งเป็นราคาที่ต้องจ่ายเพื่อให้ได้ข้อมูลที่ทันสมัย


เวิร์กโฟลว์นี้เป็นไปตามสี่ขั้นตอนของ Qiskit pattern:

- **ขั้นตอนที่ 1: แมปอินพุตแบบคลาสสิกให้เป็นปัญหาควอนตัม** เลือกอุปกรณ์และชุดคุณสมบัติที่จะวัด

- **ขั้นตอนที่ 2: ปรับปัญหาให้เหมาะกับการรันบนฮาร์ดแวร์ควอนตัม** ยูทิลิตี้นี้สร้าง Circuit การทดลองโดยตรงด้วย Gate ดั้งเดิมของอุปกรณ์ และรันแบบขนานทั่วทั้งชิป

- **ขั้นตอนที่ 3: รันโดยใช้ Qiskit primitives** การทดลองรันเป็นงาน Sampler ภายใน batch

- **ขั้นตอนที่ 4: ประมวลผลต่อและส่งคืนผลลัพธ์ในรูปแบบคลาสสิกที่ต้องการ** ฟิตข้อมูลการวัดให้เป็นแผนที่ความผิดพลาดต่อคิวบิต รีเฟรช Backend และเปรียบเทียบคุณสมบัติที่วัดได้กับค่าที่รายงานไว้

### ขั้นตอนที่ 1: แมปอินพุตแบบคลาสสิกให้เป็นปัญหาควอนตัม {#step-1-map-classical-inputs-to-a-quantum-problem}

ในเวิร์กโฟลว์นี้ "ปัญหา" คือตัวอุปกรณ์เอง อินพุตแบบคลาสสิกคือ QPU ที่คุณต้องการจำแนกคุณลักษณะและรายการคุณสมบัติที่จะวัด ส่วนการทดลองควอนตัมคือ Circuit การจำแนกคุณลักษณะที่สร้างขึ้นจากอินพุตเหล่านั้น

ขั้นแรก เลือก Backend บทเรียนนี้ใช้ `ibm_kingston` ซึ่งเป็นโปรเซสเซอร์ Heron r2 ขนาด 156 คิวบิต คุณสามารถใช้อุปกรณ์ IBM Quantum อื่นใดที่คุณมีสิทธิ์เข้าถึงแทนได้ (หรือเลือกด้วย `service.least_busy()`)

```python
service = QiskitRuntimeService()
device = "ibm_kingston"
backend = service.backend(device)
```

ถัดไป เลือกคุณสมบัติที่จะวัด คุณสามารถส่งชุดย่อยใด ๆ ของการทดลองต่อไปนี้ได้:

- `readout`: การทดลอง SPAM (state preparation and measurement)

- `rb_1q`: randomized benchmarking แบบคิวบิตเดี่ยวที่แยกอิสระ

- `rb_2q`: randomized benchmarking แบบสองคิวบิตที่รันพร้อมกัน จากการทดลอง layer fidelity

- `t2`: การทดลอง $T_2$ Hahn echo (ใช้ echo เดียวโดยค่าเริ่มต้น)

- `t1`: การทดลอง $T_1$ relaxation


รันชุดเต็มเพื่อให้ได้ภาพรวมที่สมบูรณ์ของอุปกรณ์ ตัดรายการออกได้หากคุณสนใจเฉพาะบางคุณสมบัติและต้องการประหยัดเวลา QPU

```python
experiments = ["readout", "rb_1q", "rb_2q", "t1", "t2"]
```

### ขั้นตอนที่ 2: ปรับปัญหาให้เหมาะกับการรันบนฮาร์ดแวร์ควอนตัม {#step-2-optimize-problem-for-quantum-hardware-execution}

ในบทเรียนส่วนใหญ่ นี่คือจุดที่คุณจะทำการ transpile Circuit ของคุณ แต่ในที่นี้ `BackendCharacterization` จะจัดการเรื่องนั้นให้ภายในตัวมันเอง มันสร้าง Circuit การทดลองโดยตรงด้วย Gate ดั้งเดิมของอุปกรณ์ รันการทดลองคิวบิตเดี่ยวบนคิวบิตทั้งหมดพร้อมกัน และจัดตารางการเบนช์มาร์กสองคิวบิตทั่วเลเยอร์ที่ไม่ทับซ้อนกันของ coupling map เพื่อให้ครอบคลุมทั้งอุปกรณ์ด้วยงานเพียงไม่กี่งาน เนื่องจากการรันแบบขนานนี้ ชุดทั้งหมดจึงใช้เวลา QPU เพียงประมาณ 70 วินาที

เริ่มต้นคลาสที่จัดการเวิร์กโฟลว์:

```python
# Initialize the class used to run the experiments
characterizer = BackendCharacterization(backend)
```

พล็อตเหล่านี้ต้องอ่านอย่างระมัดระวัง เพราะไม่ใช่ทุกช่องว่างระหว่างเส้นโค้งทั้งสองจะหมายความว่าอุปกรณ์ดริฟต์ไป:

- **ความผิดพลาดของ Readout และคิวบิตเดี่ยว**: ค่าที่วัดได้ใกล้เคียงกับค่าที่รายงานสำหรับคิวบิตส่วนใหญ่ ในขณะที่ค่าที่รายงานของคิวบิตไม่กี่ตัวอยู่ห่างจากเส้นโค้งที่วัดได้มาก ความไม่ตรงกันเฉพาะจุดเหล่านี้คือการดริฟต์ที่เวิร์กโฟลว์นี้ถูกออกแบบมาเพื่อจับ

- **$T_1$**: ชุดข้อมูลทั้งสองกระจายตัวรอบกันโดยไม่มีการเบี่ยงเบนอย่างเป็นระบบ ซึ่งสอดคล้องกับการที่ $T_1$ ผันผวนตามธรรมชาติเมื่อเวลาผ่านไป

- **ความผิดพลาดของ Gate สองคิวบิต**: ค่าที่วัดได้อยู่*สูงกว่า*ค่าที่รายงานอย่างเป็นระบบ นี่เป็นสิ่งที่คาดไว้ เพราะค่าที่รายงานวัดจาก Gate ที่แยกอิสระ ในขณะที่การทดลอง layer fidelity รัน Gate จำนวนมากพร้อมกัน จึงรวมผลของ crosstalk ด้วย ตัวเลขแบบเลเยอร์เกี่ยวข้องมากกว่ากับ Circuit ที่ลึก แต่ไม่สามารถเทียบกับข้อมูลการปรับเทียบที่รายงานได้โดยตรง

- **$T_2$**: ค่าที่วัดได้อยู่*ต่ำกว่า*ค่าที่รายงานอย่างชัดเจนสำหรับคิวบิตส่วนใหญ่ อีกครั้งที่วิธีการมีบทบาทสำคัญ ดังที่จะพิจารณาในหัวข้อถัดไป

#### วัด T2 ด้วยชุดพัลส์ dynamical decoupling {#measure-t2-with-a-dynamical-decoupling-train}

โดยค่าเริ่มต้น การทดลอง $T_2$ จะใช้ Hahn echo เดียวและวัดคิวบิตทั้งหมดพร้อมกัน ซึ่งจากพล็อตเปรียบเทียบด้านบนแสดงให้เห็นว่าอาจให้ค่า $T_2$ ต่ำกว่าที่ Backend รายงานอย่างเห็นได้ชัด สมมติฐานหนึ่งคือจำนวน echo ค่าที่รายงานอาจถูกปรับเทียบด้วย dynamical decoupling ซึ่งช่วยกดสัญญาณรบกวนความถี่ต่ำ เพื่อทดสอบสิ่งนี้ ให้รันการจำแนกคุณลักษณะเฉพาะ $T_2$ โดยตั้งค่า `t2_num_echoes` ให้มีค่ามากขึ้น ซึ่งจะใช้ชุดพัลส์ echo แบบ CPMG ดีเลย์แทนเวลาวิวัฒนาการอิสระทั้งหมดในทั้งสองกรณี ดังนั้นค่า $T_2$ ที่ฟิตได้จึงสามารถเทียบกับผลลัพธ์แบบ single-echo ได้โดยตรง
